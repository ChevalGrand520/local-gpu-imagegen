\title{Evidence-Bound Recovery for Ambiguous Submissions in Local Generative-AI Pipelines\\{\large Tool Description}}
\author{\IEEEauthorblockN{Anonymous submission draft}}
\maketitle
\begin{abstract}
A lost acceptance response leaves a generation client uncertain about backend execution. Our tool preserves reported state, interprets evidence through a read-only exporter, and blocks further submissions within an unresolved run. Four historical Windows/ComfyUI cases retained one execution binding per control and two per response-loss case. Their retries created fresh runs outside the guard. A subsequent same-run test stopped at model-identity validation. After the caller rebuilt pinned process-local inventory, a revised test reached the submission-outcome-unknown guard. It added no submission and left the original run unresolved. Synthetic CPU fixtures show an incomplete client operation despite worker completion. Retained raw payloads support the new lifecycle bindings; the historical event gap remains. The fixed cases demonstrate evidence export and run-scoped submission control. They establish no automatic reconciliation, deployment rates, physical GPU savings or output-quality gains.
\end{abstract}
\section{Introduction}

An image-generation client can lose a response after its backend accepts the
workflow. Without the returned job identifier, the client cannot determine
whether resubmission will repeat completed work. Request counts and timeouts
alone leave that question unanswered. Recovery therefore requires an explicit
account of the evidence available to the client and the backend.

Remote procedure call semantics already address uncertainty under communication
failure \cite{birrell1984}. Idempotent APIs make retries safe through request
identifiers and an explicit service contract \cite{aws}. Local execution leaves
the same distinction between transmitting a request and observing its outcome.
Our tool records client state and backend observations separately in a generation
pipeline; it adds no new exactly-once protocol.

The prototype combines persistent run records, a read-only evidence exporter,
and a guard that blocks submissions through an explicitly unresolved run.
Separate backend observations constrain the exporter's versioned interpretation
of client outcomes. CPU fixtures and Windows campaigns demonstrate these
interfaces under controlled response loss. Blocking a submission leaves the
original run's recovery obligation unresolved. We contribute a local
implementation that connects the run records, export decisions and submission
checks, with explicit failure boundaries. Section~\ref{sec:related} compares
these responsibilities with existing control and tracing contracts.

\section{Failure model and evidence semantics}

A \textbf{product call} is an invocation by the research client. A \textbf{run} is the
persistent product object created by \texttt{local\_gpu\_start\_run}. A \textbf{submission} in
the Windows results is a proxy-observed \texttt{POST /prompt}; a call that fails before
that boundary need not produce a submission. An \textbf{execution instance} is an
observation bound to backend execution events. CPU fixtures instead observe
the synthetic worker entry. These units are not interchangeable.

F00 is a normal control. F02 suppresses the first accepted submission response,
creating a window in which the client lacks an acknowledged job identifier.
F03, covered by the CPU fixtures rather than the Windows campaign reported
here, concerns loss of completion information after a job identifier is known.
An explicit rejection and a missing response have different evidential meanings.
Neither should be silently converted into a backend execution outcome.

The evidence model distinguishes reported state, interpreted state and oracle
state. In addition, the Windows research client emits its own call-level labels.
Its \texttt{resolved} label is derived from a generated product result after checking
for artifact hashes. Its \texttt{unresolved} label can arise from several client errors.
A research-client label alone does not establish a durable product
manifest's recovery state. In F02, the proxy's accepted-response
loss and the oracle binding provide the additional context.

\section{Tool design}

\subsection{Evidence-preserving export}

The exporter accepts a record or run manifest and produces a separate normalized
record. It copies reported state, records the mapping version and reasons, and
retains supplied oracle state separately. The schema includes source identity,
request and input digests, backend identity, job identifier, artifact hash and
validator version. Missing fields carry explicit reasons instead of fabricated
values. The inspected mapping is \texttt{research-normalization-v4}.

Interpretation checks more than an execution-success label. Job and artifact
bindings, approval and validation evidence, and recovery state constrain the
\texttt{execution\_verified} decision. An unresolved recovery state prevents this flag
from becoming true even when other evidence reports successful execution.
The current mapping also keeps recovery unknown when the reported run state is
missing and marks a disagreement between manifest and selected job or artifact
identity as an evidence mismatch. These rules prevent omission or a top-level
field from silently strengthening the composite decision.
A record can therefore report backend completion while leaving the product's
recovery obligation unresolved. The exporter does not
invoke the engine, retry a request or update the source run. Its output writer
uses exclusive file creation. These are implementation properties, not a
claim of complete filesystem security.
The interpretation assumes that supplied oracle and artifact-validator records
have trustworthy provenance. The exporter checks their stated fields and
bindings; it does not authenticate their origin or reconstruct missing raw
events. In the current mapping, absent source revision, backend-instance or
validator-version metadata need not by themselves prevent
\texttt{execution\_verified}. That flag denotes satisfaction of this mapping's
evidence policy, not independent certification of the input record.

\subsection{Using the evidence record}

An investigator first inspects the run manifest and the recorded submission
outcome. If submission is explicitly unknown, inspection must preserve that
uncertainty: the missing job identifier must not be synthesized from a later
successful call. Backend observation is then associated with the relevant
request and execution instance, while artifact checks retain their own result.
The export command writes a new record and refuses to overwrite an existing
export:
\begin{quote}\small\ttfamily
python -m\\
scripts.research.export\_records\\
--input run-record.json --output evidence.json
\end{quote}
The output exposes reported state, interpretation, mapping reasons and supplied
oracle evidence without initiating recovery. Missing oracle evidence remains
missing. The Windows observer and exporter use separate schemas; the offline
conversion described below bridges retained inputs rather than providing
automatic live conversion.
The companion offline demonstration supplies two synthetic records that differ
in the original run's status. It also normalizes twelve previously retained
CPU product manifests alongside their fixture oracle records, without adding
artifact-validation assertions. All twelve remain unverified by the composite
policy. This demonstrates the mapping's behavior on retained product records,
not an independent replay or certification of their original events.

The exported record can contain successful backend evidence, required recovery
and false execution verification. A later successful call leaves the original
run's unresolved state intact.

\subsection{Recovery guard and its scope}

\texttt{AssetRunEngine} and \texttt{RunStore} preserve the explicit transport marker
\texttt{submission\_outcome=unknown} as an unresolved attempt. The reviewed submission
entry checks that unresolved attempt before permitting further generation.
The guard applies within the same run, including attempts with a different
idempotency key. The corresponding inspection action is \texttt{get\_run}.

The guard neither discovers a missing job identifier nor reconciles an unknown
job. A new run lies outside its scope. Known-job recovery in two-stage operations
uses a separate path. Withholding another submission leaves the outcome
uncertain and supplies no completion guarantee.

A pipeline integrator can use this distinction when a generation UI receives a
disconnect after sending a request: the exporter preserves the unknown outcome,
the same-run entry blocks another submission, and the operator must inspect or
reconcile the run through an available backend-specific mechanism. The guard can
also conservatively withhold work when a request failed before backend acceptance,
which is a potential false-positive direction. In the accepted-response-loss
CPU fixture, the observed cost is an incomplete client operation; eventual
completion is not established.


\subsection{Controlled observation on Windows}

Figure~\ref{fig:architecture} shows the product and research boundaries.
The research harness adds a transport shim and loopback fault proxy. The shim
routes prompt transport through the proxy while retaining the actual backend
endpoint in the product's identity client. F02 drops the first response only
after backend acceptance. This arrangement is a research instrument, not a
native ComfyUI recovery feature.

The observer connects before the product invocation and uses the operation key
as its ComfyUI client identifier, matching the product's event-routing identity.
\texttt{ComfyUIEventOracle} requires an execution-start event, a terminal event and
completed history bound to a prompt identifier. It derives an execution-instance
identifier using the backend boot identity, prompt identifier and observed
start sequence. Its independence is from the product return value: it still
trusts the backend's event and history interfaces, and it is not a physical GPU
monitor or a crash-durable audit log.

The controller permits the second F02 product call only after the first
execution has a bindable completion. In this historical protocol, the client creates a new run on each call
and uses \texttt{seed = 4100 + call\_index}. This is observation-gated fresh-run
generation, not automatic reconciliation of the original run. Because the new
run is outside the same-run guard, the Windows campaign does not measure the
guard's blocking effect. CPU F02 fixtures exercise blocking; in the single-stage
fixture, W3 has one execution rather than B2's two, while leaving the operation incomplete. Matching frozen
request digests does not establish full prompt equality: the inspected digest
function excludes the seed and does not use its plan argument.

\section{Evidence and demonstration}

\subsection{CPU components and deterministic fixtures}

We denote the frozen baseline product revision by B2 and the revision with
the same-run ambiguity guard by W3. The CPU harness separates submission events from synthetic worker-entry events.
Its fixtures cover normal operation and response loss before and after job-ID
acquisition, including single-stage and two-stage paths. Oracle self-checks
exercise cases in which submission and execution counts differ and in which a
shared prompt identifier does not imply a single execution. These are fixed
semantic checks, not randomly sampled deployments.

The delivered offline checks were tested with Python 3.13.15. Their source
requires Python 3.10 features; compatibility with 3.10 itself was not tested. They check retained-record consistency and mapping,
not backend execution. Historical test-count and runtime claims without packaged
receipts are omitted. Exact historical CPU test-worktree attestation remains
unavailable. The Windows v1/v2 campaigns recorded nine harness source hashes
each. Separate source snapshots reconstructed from the respective Git revisions
with Windows CRLF bytes match all eighteen recorded hashes. A packaged verifier
checks this correspondence; byte matching is not runtime execution attestation.
The current research caller is not substituted for either execution snapshot.

a \texttt{partial} reported run maps to unknown recovery, rather than no recovery

any execution or submission count. Reanalysis checked

The campaign totals were six calls, six proxy submissions and six retained bound
execution instances. The F02 second call used a fresh run and changed seed.
The four report records matched the corresponding retained JSONL cases.
Their six retained execution bindings had distinct identifiers, completed-history
flags and terminal-event labels. In both B2\_F02 and W3\_F02, the export reports
\texttt{execution\_start=3}, two proxy submissions and two retained bindings.

Each F02 case has two observer decisions. The oracle's \texttt{raw\_events}
field is cumulative, while the export counts the entire event list of each
decision. For example, if the first list contains start A and the second
contains A and B, the sum is $1+2=3$ entries for two distinct starts. Each F00
case has only one decision, so this recounting opportunity is absent there.
The uniqueness check concerns the two retained binding identifiers per F02
case, not the three aggregate entries. This source-level mechanism makes the
reported count compatible with two bindings; it does not reconstruct the
historical lists. Because the original snapshot boundaries and payloads are
unavailable, an additional unbound start cannot be independently excluded.
We report two retained bindings per case, not a complete execution ground
truth.

The first binding's completion precedes the second
receipt, as required by the controller's observation gate; these timestamps
belong to different calls. No rate is estimated. Here, ``oracle-evaluable''
refers to the retained binding record, not an independent raw-event audit.

The report identifies an RTX 5070 Ti Laptop GPU and ComfyUI v0.30.0 at a pinned source revision, with model and workflow hashes
checked against the campaign configuration. These are recorded environment
facts for this campaign. They do not establish behavior across other models,
backend versions or machines.

The research export retained execution identifiers despite the first call's
ambiguous outcome. The cases provide no execution-count advantage for
W3. Changing both run and seed also prevents interpreting them as repeated
executions of an identical generation request.

The cause of the identity disagreement is unverified; its error code does not

A revised \texttt{same-run-guard-v2} caller rebuilt the pinned model inventory
in both fresh MCP processes, using the existing exact-file index, fingerprint
and private-catalog checks. It reused the complete generation arguments within
the same run, without changing the frozen product or bypassing locked-route
validation. In a separate two-case
campaign, the F02 retry returned \texttt{submission\_outcome\_unknown} at generation.
The controller reported \texttt{submission\_guard\_observed=true}, with one total F02-case
POST and an unchanged unresolved manifest. The retry thus reached the target
guard and was blocked in one fixed response-loss case. The original run was
not reconciled, and eventual completion remains unestablished. The setup change supports a process-local
inventory explanation for v1, without proving its entire internal error path.

Each campaign's private capture retained 90 F00 and 10 F02 WebSocket text payloads and one
history response per case. Offline reanalysis checked byte hashes and channel
sequences, reconstructed one start and one \texttt{executing} event with
\texttt{node=null} per case, and bound them to successful history and the
published execution identifiers. This reanalysis checks the received, retained
evidence without authenticating it or establishing completeness. Both controls
and F02 cases included cache events. In F02 the cached-node list contained
nodes 3--9; there were zero \texttt{progress} messages but one
\texttt{progress\_state} message, so its lifecycle binding is not evidence of new
physical GPU computation. These new payloads do not recover the missing
historical event lists. No third call or fresh-run fallback was made.

\subsection{Resolution labels require an explicit aggregation rule}

A resolved second call does not erase the first call's unresolved result or
show that its original run was reconciled. Read-only inspection of the retained
campaign report confirmed that both F02 records carry \texttt{resolved=1} and
\texttt{unresolved=1}. These are independent any-call flags: across the four cases,
\texttt{resolved} sums to four and \texttt{unresolved} to two. They are overlapping counts,
not mutually exclusive outcomes. The earlier Markdown summary's zero unresolved
cases is therefore not the controller aggregation. Table~\ref{tab:cases} preserves the call
sequence; the evidence addendum records this correction without rewriting the
historical report. No recovery-success rate is inferred.

\section{Reproducibility and limitations}

The CPU records retain product revisions, harness digests and event traces.
The companion ledger identifies Windows sources and reports. Audit and figure
scripts reanalyse these records offline; reproducing a Windows campaign also
requires its pinned backend, model, workflow and private setup. The historical
four-case campaign was not rerun. Separate same-run campaigns preserved the
frozen product and retained both the v1 failure and v2 observation.

Historical JSONL contains sanitized summaries, bindings, terminal labels and
aggregate counts, without complete WebSocket payloads or history snapshots.
Its audit checks consistency and regenerates two tables, but cannot reconstruct
every backend event. The oracle requires \texttt{executing} with \texttt{node=null}
and completed history. The exported terminal label lacks that discriminator
and is set by construction, so checking it does not independently prove
completion. Report/JSONL equality and image-byte matches remain historical
inspection receipts rather than checks repeated by the offline script.

Host-side hashing matched the four generated-call artifact hashes to retained
image bytes, with one product-output PNG per case. The first, unresolved F02
call recorded no product artifact hash; those checks therefore do not verify
its output bytes. Oracle path fingerprints hash metadata rather than image
content. Neither content hashes nor completed history measure visual quality
or final user acceptance.

The observer must receive and bind events within its capture window. Missing
events limit what the observer can evaluate; their absence does not prove
non-execution. CPU and Windows observers
have different failure boundaries; neither provides crash-complete auditability.
The fixed cases support no population rates, performance gain or broad model
robustness claim. The subsequent Windows campaigns used existing models and
remain separate from historical observations. In particular, v2 supports one
fixed-case guard observation, not an execution-count advantage. Private raw
captures are excluded from delivered archives, limiting third-party reanalysis
to the included evidence rather than the original received bytes.

The offline Windows conversion maps the retained product manifest separately
from its audited backend lifecycle. F00 yields succeeded execution, partial
evidence and no recovery requirement; F02 yields succeeded execution, missing
evidence and required recovery. Neither is composite-verified: no independent
artifact validator was supplied. Four variants (two missing-state and two
job-identity-conflict) are explicitly synthetic checks, not additional Windows experiments.
They retain unknown recovery or mismatch evidence. A clean-copy replay preserved
all input bytes and reproduced the interpretation summary. The anonymous demo
provides whitelisted, pseudonymized semantic projections whose interpretation
states match the private conversion; it reproduces mapping, not raw-event audit.

\section{Related work and discussion}
\label{sec:related}

Observation and control answer different questions at an uncertain submission
boundary. A backend lifecycle can complete while the client still requires
recovery; blocking a further submission does not discharge that obligation.
RPC semantics and idempotent service contracts already address ambiguous
outcomes and safe retries \cite{birrell1984,aws}. Our tool instead records the
evidence available when backend deduplication is unestablished. Neither a
prompt identifier nor a client idempotency key alone supplies that guarantee.

Li's preprint compares model, harness and tool-contract effects on duplicate
side effects in a simulated service benchmark \cite{li2026exactlyonce}. Its
guard combines read-back, supported idempotency keys, delayed verification,
blocking unverifiable repeats and uncertainty annotations. Our narrower guard
blocks an explicitly unknown submission within one run, without automatic
read-back or reconciliation. Withholding unsafe retries is therefore not our
novelty claim. Our contribution is the local implementation that preserves
reports and links their interpretation to backend observations. Different
workloads and evidence sources preclude comparing the studies' outcome counts.

Reliable State Machines use persistent state and atomic runtime processing
to support failure transparency and exactly-once input processing
\cite{rsm2019}. Our external generator remains outside such a transactional
runtime. Temporal likewise documents that completed Activities may be retried
after a worker crashes before reporting completion, and recommends idempotent
Activities \cite{temporal}. These contracts explain why durable client state
alone cannot settle external side effects. Our restricted submission entry
provides neither equivalent workflow guarantees nor automatic reconciliation.

OpenTelemetry relates operation spans through trace context \cite{otel}.
Our application-specific policy additionally requires backend start and terminal
events bound to completed history, while unresolved recovery vetoes
\texttt{execution\_verified}. Correlation identifiers alone are not execution counts.

Toxiproxy injects configurable TCP connection faults \cite{toxiproxy}. Our
proxy selects an accepted application response for suppression while a separate
observer checks its lifecycle. No comparative implementation or usability study
was performed, so equivalent Toxiproxy setups are not ruled out. Filibuster's
project overview describes synthesizing fault-injected variations from integration
tests \cite{filibuster}. Our fixed submission cases offer no such search coverage;
this comparison uses the overview, not reproduced Filibuster results.

These comparisons use the documented contracts to define each tool's
responsibilities. They establish no superiority, exhaustive novelty or
developer productivity gain. Within the evaluated workflow, our records let a
reader inspect the client's ambiguous outcome, the backend observation and the
claims those observations support.

\section{Conclusion}

The tool records ambiguous client outcomes alongside bound backend observations
and restricts further submissions through an unresolved run. Historical Windows
cases distinguish a successful fresh-run call from original-run reconciliation.
Same-run tests retain both a masking failure and one fixed-case guard observation.
The original run remains unresolved, and blocking another submission supplies
no physical GPU-savings evidence. Automatic unknown-job recovery, deployment
reliability and natural duplicate-execution rates remain unestablished.
