# Bounded integration decisions (declared before implementation)

- Source base: experiment/spe-recovery-validation at 054e7b6. The October 6 known-ID/manual-history equality is retained negative evidence.
- Upstream: artokun/comfyui-mcp 6996d06ff511dd7b3b05adf89716e7667df2c1b9, package 0.52.206, MIT. No upstream files copied into the product or upstream modifications.
- Interface: Python stdlib client speaks newline-delimited stdio MCP to a separately installed upstream server. It calls existing enqueue_workflow action=enqueue (upstream preserves supplied seeds) and get_history action=list with exact prompt_id.
- Scope: an experimental client, not a replacement MCP server or reuse of the product RunStore. It adapts the same durable intent/unknown/known-ID mechanism in SQLite so the experiment can isolate the upstream MCP boundary.
- Semantic: one logical operation per run_id. A planned new generation needs a new run_id. Requests bind key, canonical graph, endpoint identity and upstream command; same graph order changes are equivalent.
- Semantic: endpoint identity is supplied explicitly and must correspond to the upstream server's configured endpoint. This client cannot independently establish that correspondence. It freezes the command and environment at client initialization; subsequent backend/model changes are outside the guarantee.
- Semantic: record intent BEFORE invoking upstream. Any unsuccessful call, malformed reply or process death after intent leaves uncertain submission and prevents resubmission, even if no POST happened. Known-ID history read is read-only; this does not label a run generated/completed or download/accept images.
- Controls: native delegates without a durable guard; stop uses the same journal but same-key submit does not read history; full uses same-key submit to read known history. BOTH journal modes expose explicit read_history, so manual history recovery is not denied to the baseline.
- Semantic: persist job ID as soon as the MCP call returns; upstream accepts at HTTP before MCP reply, leaving a response-loss / before-binding uncertainty window. No missing-ID matching or reconciliation is attempted.
- Concurrency: SQLite BEGIN IMMEDIATE reserves a run before I/O. An abandoned intent is never stolen or auto-cleared; same-run competing clients stop. SQLite FULL synchronous on a local filesystem; network filesystems and machine power-loss validation deferred.
- Output: store workflow digest and MCP results, not the workflow itself or credentials. MCP result content can contain backend information; journal/output are private local state, never public experiment artifacts by default.
- Authorization: local CPU checks and dependency setup only. No actual GPU/ComfyUI job, model download, upstream issue/PR or stable merge.
- Runtime environment binding hashes COMFY* and MCP_* variables (values are not persisted). Backend configuration files and upstream binary content changes are not detected; use the pinned checkout and keep configuration fixed. Credential changes conservatively cause a conflict.
- Follow-up independent baseline: MinimalClient uses a separate SQLite schema, raw canonical request/context comparison and explicit exact-ID history retrieval. It shares only MCP wire transport and response ID parsing with the adaptation, not journal or request binding code. Its local database stores raw request and COMFY*/MCP_* environment, potentially including credentials: private local state only. The baseline compares equal-information handling; no uniqueness advantage is presumed.
