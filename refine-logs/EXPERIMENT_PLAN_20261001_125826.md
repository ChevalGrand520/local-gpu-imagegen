**研究题目**：Evidence-Bound Recovery for Ambiguous Submissions in Local Generative-AI Pipelines

**日期**：2026-10-01，Asia/Shanghai。

**状态**：FROZEN_DESIGN / NOT_RUN / IMPLEMENTATION_GATES_OPEN。
本次批准覆盖协议准备；本文不构成 Windows/GPU 启动回执。旧版 2026-09-28

## 问题与主张

客户端缺少接受回执时，允许再次提交与保留原 run 的未决义务之间存在取舍。
我们研究提交控制及证据解释；模型保持现有版本，不训练新模型。

| 主张 | 最小证据 | 模块 |
|---|---|---|
| C1：显式 unknown 的同 run 守卫约束追加提交，且其完成代价可被共同记录 | 原生 B2/W3 同输入、同故障、同重试时点；POST、接受、生命周期和原 run 完成分别计数 | B0、B1 |
| C2：导出保留后端完成与原 run 未决的分离，并暴露缺失或冲突的证据 | 完整/删字段记录与独立答案；恢复未决时验证 flag 的行为；输入字节不变 | B0、B2 |

反解释：低 POST 可能来自 caller 前置拒绝、同 key 缓存、代理未收到请求、模型身份
校验或简单 stop 策略，而非产品守卫。导出与同信息的普通解析脚本也可能判定完全相同。
出现这些结果时照实收缩主张，不靠扩大样本制造优势。

## 故障与首批矩阵

新协议名称为 `paired-ambiguity-v1`。F00/F02 保留原义；新增研究故障命名 `FPRE`，
不改写任何历史 F02 标签。

| 条件 | 注入点与独立判据 | 每边计划调用 | 研究问题 |
|---|---|---:|---|
| F00 | 透明代理；接受回执正常送达 | 1 | 产品入口、模型路由和完成证据是否健康 |
| F02 | 代理收到成功接受响应及 job ID 后，压制首次回执 | 最多 2 | accepted-but-unknown 下追加 POST、生命周期及完成代价 |
| FPRE | 代理已读完请求体，在调用上游发送函数前记录注入并关闭连接 | 最多 2 | 可证明首次未送达后端、客户端却 unknown 时的保守阻塞 |

首批：3 条件 × 2 产品 = **6 个操作、3 个 pair**，一个固定 seed。
最多 10 个产品调用和 10 条代理 POST。FPRE 首次两条 POST 均不转发，故全批最多
8 次上游请求尝试；接受数和生命周期数必须实测，不能用该上限代替结果。

顺序固定：F00 B2→W3；F02 W3→B2；FPRE B2→W3。后续重复若被批准，采用预先
平衡的顺序，不按结果挑 seed。每操作使用新的 run、代理、observer session 和证据目录。

F02/FPRE 的第二次 generation 调用安排在首次调用结束后 **1.0 秒**，受剩余 deadline
约束；不等待 observer 确认完成，不向客户端补 job ID。重试同 key、同参数。
首批用于协议检验与个体配对结果，不能据三组 pair 估计自然故障或重复执行频率。

### FPRE 真值要求

必须保留 `body_received → fault_injected_before_upstream → connection_closed` 的
追加式阶段记录，并证明发送函数未调用、该操作没有绕过代理的 prompt 路径。
`accepted_job_id=null`、缺少 WebSocket 消息、客户端超时或 `forwarded=false` 单独均不够。
若客户端得到明确拒绝而非 unknown，归类为明确拒绝对照，不能计入保守阻塞分母。

### 缓存策略

每操作在独占的研究 backend process 中起始；两产品使用相同已核实的启动/缓存策略。
进程隔离不等于物理 cold-compute 认证：记录全部 cached-node、progress 与 history 字段。
**同一操作的第一次和第二次调用之间不重启 backend、不清缓存、不变参数。**
缓存复用是实际策略轨迹的一部分；不能为制造第二次 GPU 执行而干预其中一边。
发生缓存复用仍可分析 POST 与生命周期，但本轮不据此计算 GPU 节省。

## 三个必需模块

### B0：可达性与测量自检，CPU

- 三策略：原生 B2、原生 W3、caller 层 `P-stop`；P-stop 在客户端明确 unknown 后
  只保存/检查记录，不发起第二次 generation。其服务端产品基底固定为 B2。
  三策略共享可见客户端信息的 unknown 分类规则在 M0 冻结，不能给 P-stop 提供代理
  或 observer 的独享真值。若 B2 缺少所需客户端信息，先修订策略定义，不编造字段。
- 3 策略 × 3 故障 = 9 个合成操作。另加 W3 的健康同 key 重放、unknown 下新 key、
  unknown 后新 run 三个 scope probe，共 12 个合成操作；新 run 不计入同 run 收益。
- 使用完整产品入口及可控 CPU backend；工作开始/完成事件给出独立构造真值。
  不能直接调用内部守卫、改 manifest 或仅构造预期 JSON 冒充路径测试。
- 验证 FPRE 未发送真值、F02 接受真值、事件 snapshot 去重、artifact byte hash、
  调用顺序、同输入 digest，以及早于守卫的身份/参数拒绝分类。
- 健康 replay 需明确可用的产品 action/round 预算；其他约束拒绝不能误称 guard。
- 通过：所有已知构造判据一致、原生入口可达、无上游来源认证虚报、无不明计数差异。
  旧 61 tests 和旧 B0 20 条构造记录仅是历史基础，不是本模块已经通过。

### B1：Windows 最小配对试跑

- 执行上述六操作；两产品的 F00 控制先通过，才进入故障 pair。
- 首批仅比较 B2/W3。P-stop 的实机比较留待新预算版本；CPU 等价结果照实报告。
- 首要成功条件：W3 真正进入 generation 并返回 submission-outcome-unknown 守卫拒绝，
  追加 POST=0、原 run 仍未决，且提交边界和实际调用路径具有可核查记录。
- 与 B2 的差异只按实测报告。若 B2 同样不提交，不宣称比较优势；若路径不可达则停止。
  若只见零 POST 而无可定位产品拒绝，不归因为 guard。完成不利结果同样保留。
- 图表：每个 pair 的 POST/接受/生命周期、原 run 完成、阻塞原因联合表；时延显示
  个体值和删失，不制作没有独立硬件计量的 GPU-cost 图。

### B2：证据解释与简单策略诊断，CPU/离线

- 将保存的记录提供给两种同信息视图：显式契约 exporter 与普通字段解析脚本。
  二者看到相同输入；答案来自独立 proxy/worker/manifest 记录，不来自待测 exporter。
- 构造最多 12 个探针：完成+恢复未决、已知完整、身份冲突、缺关键证据，每类三条。
  完成+未决探针须补足其他验证条件，以隔离 recovery veto；不靠缺 artifact 使 flag 为 false。
- 指标：错误肯定数、正确判定数、unknown 数、输入不变性及理由可定位性。
  若解析脚本完全相同，只支持可检查结构与整合，不声称增加了信息或提高判定准确率。
- P-stop 与 W3 等价时保留该结果；本研究不把 run 守卫包装成新的自动恢复算法。
- 不开展人类参与者研究，不把脚本耗时称为开发者效率。

## 指标与单位

每条结果关联 operation/pair/run/call/attempt/submission/job/observer 身份。

| 指标 | 定义与分母 |
|---|---|
| S_proxy / S_upstream / A | 代理收到 POST 数、真正开始上游发送的请求数、具有接受回执的 job 数；分别计数 |
| additional_POST | 首次调用之后由重试产生的代理 POST 数，按操作/条件展示 |
| E_bound | 基于唯一开始+node-null 终止+completed history 的生命周期数；累计 snapshot 不求和 |
| additional_lifecycle | 同语义操作中 `max(0,E_bound-1)`；不可判定时 unknown，不填零；不是重复 GPU 计算 |
| client_completion | deadline 时原 run 的持久完成状态和有效产物证据；caller resolved 单列 |
| conservative_block | 已证明首次未上游发送且客户端 unknown 的操作中，guard 拒绝数/该条件有效操作数；不是部署误报率 |
| call/recovery latency | 使用同机单调时钟；第二次 generation 请求到返回的整体耗时，含 MCP/路由开销，不能称纯 guard latency |
| completion latency | 从首次 generation 请求至原 run 约定完成；未完成者报告 `>T`/删失，不只平均成功者 |
| evidence coverage | 有效且可判定操作数/计划操作数；注入失败、基础设施失败和超时另列，不删样本 |

无上游发送的 FPRE/W3 由闭合的代理路径证明本操作未触发 backend 请求；其代理 POST
仍须计为一次。任何已接受 job 若缺完整 binding，E 为 unknown。生命周期、产物文件
与 GPU 物理计算保持分层。

## 记录合同与保留

- 在 backend 启动前保存运行配置、完整代码快照、实际 LF/CRLF 字节哈希、产品 revision、
  Python/ComfyUI/模型/workflow 身份；不得在采集后重构源码代替执行时快照。
- caller 在实际 generation RPC 前/返回后追加请求事件及单调时钟，保存全部参数与
  before/after manifest 字节。产品内部 guard trace 若需插桩，标为插桩变体，不能冒称
  untouched B2/W3；原生产品结果与研究 caller 的路径记录分开。
- proxy 记录接收、发送开始、请求体发送、接受响应、压制响应等阶段，不用单个布尔值
  覆盖发送状态。raw WebSocket、history snapshots、snapshot 边界、原 node 字段完整保存。
- artifact 独立读取字节重算哈希；失败或缺失保留理由，exporter 不假定验证成功。
- 同机 monotonic 和 UTC wall clock 均保留；跨进程配对同步与误差界明确记录。
- 原始私有目录不公开，公开投影需逐字段审查并保留私有映射。作者 ZIP 不作为匿名材料。
  数据追加、目录独占、禁止覆盖或删除失败样本。

## 执行顺序、预算与止损

| 阶段 | 安排 | 当前状态 | 上限 / 继续门槛 |
|---|---|---|---|
| M0 | caller/proxy/controller 适配及 B0、B2 自检 | NOT_RUN；有静态缺口 | CPU 批次 30 分钟、最多 12 操作+12 探针；全部已知判据通过 |
| M1 | 冻结 Windows 现场配置与 source bytes | PENDING | numeric-IP SSH、实际公钥/agent、模型/backend身份、独占预约、新目录、清理 owner 全部核实 |
| M2 | F00 B2/W3 控制并校准 deadline | NOT_RUN | 最多两次生成；每个控制硬截止 300 秒；任何控制失败即停止 |
| M3 | F02、FPRE 两组 pair | NOT_RUN | 故障操作 deadline `T=max(60s,3×max(F00 completion))`；若计算出的 T>300 秒则停止修订，不截短 T |
| M4 | 配对分析与升级裁决 | NOT_RUN | 主张按结果更新；无新增生成、无外部模型审查调用 |

首批资源硬上限：一个已预约 GPU、60 分钟墙钟，包含启动/重置/清理；6 操作、10 调用、
10 代理 POST、8 上游发送尝试；采集存储 1 GiB。任何上限先到即停止。无云付费；
这是预算上限，不是完成时间/GPU 实际消耗预测。实现工作暂估 1–2 个人工作日，主要风险
是 B2 入口适配与发送阶段真值；健康校准前不给单次生成成本估计。

模型/输入漂移、非目标拒绝、注入判据失败、调用路径缺失、健康对照失败、计数无法重建、
关联身份冲突、资源冲突、超预算即 STOP，保存部分记录。只终止本 campaign 拥有的服务。
修复后的重跑使用新配置版本和新 campaign ID；本预算不允许隐式补跑失败操作。
三种 seed、多模型、P-stop 实机比较、GPU 硬件计量和 100/1000 次重复均为后续版本，
不能由本协议自动扩大。启动许可需与当时的有效预约共同成立，计划批准不替代资源门槛。
