# ISSRE Regular 有界可行性验证

日期：2026-09-28。作者侧源码分析和小型 CPU 检查；不构成独立同行评审或全面查新。

## 决定

**当前实现不足以支持“判定能力优于普通日志加审计脚本”的 Regular 主张。暂停扩大实验；保留 Tool 的工程贡献。**
这不是证明所有未来方案不可行，也不是仅凭相关论文否定独立工作。

## 已执行

- 读取 `export_record`、`_interpret_state`、oracle contradiction、evidence 和 recovery 判定。
- 两个完整摘要的构造案例：generated 与 unresolved，其余证据相同。脚本与原始输出分别为 `scripts/research/check_regular_feasibility.py`、`docs/research/runs/regular-feasibility-witness-20260928.json`。
- 11 个现有 exporter 单元测试通过（0.003 秒）；这与两条构造记录不是13个独立科学样本。
- 无 GPU、无真实后端、无外部模型、无72案例 campaign。未改生产代码或论文结果。

## 三个决定性观察

1. **同信息不产生信息增量。** exporter 是输入记录的确定性转换。若基线获得同样完整记录并允许实现同样规则，就能重建这些输出；不能以格式规范化本身声称获得额外事实。标准化、可维护性、错误预防仍可能有工程价值，但需要各自的评价设计。
2. **已测局部规则并不复杂。** 在冻结的两条完整摘要中，简单检查 run 是否 generated 即可匹配综合 verified。这个基线只适用于这两条记录，不能推广为全部输入等价，也不作为准确率比较。
3. **输入来源是受信前提。** supplied oracle 的成功/可评估标记和 artifact validator 的 independent 标记参与判定；source_sha、backend_instance、validator_version 可缺失而仍 verified。输入记录本身可以由调用者提供。这不能证明实际被攻击或发生错误，但不能据此声称 exporter 认证了独立观察、原始事件完整性或记录来源。

同一个输入记录可以被描述为来自正确实验，也可以是未经认证的历史拷贝；exporter 没有额外观测就无法区分。该逻辑限制不是新发现的普适理论，也不是部署故障率证据。

## 对 Tool 论文的影响

应明确：versioned interpretation 是在所声明的输入来源可信、字段语义成立前提下进行的记录解释；`execution_verified` 是该工具的综合策略标签，并非认证原始事件或端到端恢复。
当前生产实现按既定契约可正常工作；“没有更强保证”不能直接称为实现 bug。
不将研究用 `cpu_evidence_contract.py` 的构造检查冒充已部署 exporter 的功能或真实后端验证。

## 什么才值得开启新的 Regular 提案

不是增加 seed 或改标题，而是选择一个有实际用户需求的保证，例如跨进程记录关联与证据不完整下的可靠拒绝判定，并明确：
- 信任根、事件来源、故障模型及完整性前提；
- 普通完整日志加审计脚本、现有 tracing 能做到什么；
- 我们新增的采集/持久化/验证机制，以及可证伪的性质；
- 正确肯定、错误肯定与拒绝判定的联合代价。

这将是方法建设，不是原稿补实验。预计工作量不能沿用此前矩阵实现的3–5天估算。本轮不授权或启动该新方向。

## 继续投入建议

ISSRE Regular 暂作为条件目标，不作为当前最优性价比结论。先完善 Tool 的信任边界和可检视工件。IEEE Access 同样不能规避方法/证据不足；“SCI三区”仍是未完成年度分区核验的规划标签，不是确认事实。

结论强度：已证明具体受信边界、验证局部简单基线；尚未证明工具毫无价值、所有方法无创新、或任何投稿必然被拒。
