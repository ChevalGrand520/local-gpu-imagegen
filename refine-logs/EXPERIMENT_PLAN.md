# Regular 版本补证提案

日期：2026-09-28。状态：PROPOSED / NOT RUN。
写作基线：3edc489；历史实验基线：5cd100f2b4a4a7aaeac1fd707fc248bae46f239c。
本文件是提案，不是实验预注册完成证明，也不是执行授权。

## 问题与贡献假设

问题：客户端不知道提交是否被接受时，重试可能增加执行，阻止重试又可能牺牲最终完成。现有 Windows campaign 使用新 run，不能回答同一 run 守卫是否有效。
主张候选：显式保存提交不确定性并限制同一 run 的后续提交，可在指定故障条件下约束额外提交；其完成代价必须同时报告。
辅助主张候选：保留逐调用事件与判定来源，可以识别仅看客户端状态或累计事件数会产生的错误解释。
反解释：收益可能仅等同于“未知时永不重试”；证据导出也可能只是已有日志的重新包装。若无法排除，不升级为 Regular 贡献。
本研究不提出新生成模型，不训练模型，不主张生成质量提升；无需为“生成式 AI”标签加入额外模型。

## 主张与最小证据

| 编号 | 候选主张 | 最小证据 | 模块 |
|---|---|---|---|
| C1 | 同 run 守卫明确改变提交/完成之间的取舍 | 同输入同故障的成对对照；包含简单停止策略；同时记录执行、完成、误拦 | B1、B2、B3 |
| C2 | 证据契约能暴露状态与执行之间的歧义及缺失 | 可独立重建的记录；预先指定缺失/重复事件挑战；错误肯定与不可判定同时报告 | B0、B4 |

这两项仍不保证创新性或录用。正式运行前必须完成最近工作比较，确定与现有幂等重试、工作流恢复、追踪和故障注入工具的实质区别。

## 比较系统与共同规则

最多三个策略族：
1. P-retry：B2 对应的恢复路径，至多一次追加提交；必须验证它能走与 W3 相同的同 run 入口。若不能，标注为研究适配策略，不冒充原生 B2。
2. P-stop：显式 unknown 后不再提交、只检查状态的简单基线。与 W3 使用相同超时和检查预算。
3. P-guard：W3 守卫路径。不得让它独享研究 oracle、额外查询或人工恢复。

oracle 只测量，不为任一策略作恢复决定。若比较使用 oracle 辅助恢复，必须单列为额外方法，另行提案。
每个逻辑操作先分配 operation_id；同组策略使用相同 workflow、模型、seed、输入及故障位置；身份 token 可不同。保存规范化语义输入哈希（包含 seed）和传输请求哈希，不用缺 seed 的旧 digest 证明输入相同。
新 run 另设 scope probe：沿用同一逻辑 operation_id，明确它位于守卫范围外，不用于计算同 run 机制收益。
不把不同 seed 的正常新生成请求称为重复执行。

## 五个实验模块

### B0：可审计记录与判定检查（必需，CPU）

- 输入：人工定义的事件序列，无学习数据划分；新脚本与历史样本分开。
- 保留：operation/run/call/attempt/job/event 身份、顺序号、单调时钟及时间源、故障触发与接收记录、原始 terminal node、history completed、所有事件快照边界、内容哈希。
- 对照：完整记录与移除身份/terminal 字段/快照边界的删除版本；每次只删一个因素。
- 挑战：正常完成、重复快照、重复事件、乱序、事件缺失、terminal 非空 node、history 不完整、进程重启后关联缺失。
- 成功标准：每条已知构造的判定与预期一致；缺关键证据必须变为 unknown，不能虚报 verified；重复输入不增加去重执行数。保留全部失败。
- 负结果：若连构造记录都不能可靠解释，停止后续运行，先修测量工具。
- 输出：证据 schema 示例与判定混淆表；这是已知构造的正确性验证，不是部署准确率。

### B1：同 run 机制覆盖与健康对照（必需，CPU）

- 固定单阶段工作流，三策略，对五个故障位置：F00 无故障；明确接受前失败；实际未接受但客户端被标 unknown；接受后回执丢失；已知 job ID 的完成回执丢失。
- 每格固定三个调度顺序：恢复尝试早于完成、与完成交错、晚于完成。F00 保留相同顺序调度作为健康配对。
- 共 3×5×3=45 个逻辑操作；worker entry 为独立于客户端返回值的合成执行观察点。
- 必须记录实际调用的入口和原 run 身份，不能通过直接改 manifest 或内部函数冒充完整产品路径。
- 成功标准：W3 在预期 unknown 同 run 路径上阻止追加提交，健康路径可完成；P-stop 的相同性/差异如实保留。
- 负结果：与 P-stop 等价只证明策略边界，不证明新恢复机制；不得继续靠增加样本包装优势。
- 图表：五种故障位置×策略的提交、执行、完成、阻塞表。

### B2：真实后端的有界同 run 对照（必需，但须另行批准 GPU）

- 仅使用现有本地模型与工作流；先确认可用性，不下载替代模型。
- 三策略×三个条件（健康、接受后回执丢失、实际未接受但客户端 unknown）×三个配对 seed =27 个逻辑操作。
- seed 具体值在冻结配置时选定并记录，策略间配对。三 seed 用于覆盖，不当成充分统计功效。
- 每操作最多两次 backend submission，理论最多 54 次候选执行；实际以观察记录为准。
- 超时由先行健康校准固定：T=max(60 秒, 3×校准最大完成时长)，但 T 不得超过 300 秒。需要更长则暂停修改提案。
- 成功标准：B1 的核心取舍在真实提交路径可见，且原始记录可重建。不能要求“既零额外执行又全部完成”来隐藏系统做不到的能力。
- 未接受 unknown 只有在受控注入能证明没有转发/接受时才计入该条件；客户端错误本身不构成未接受证据。
- 图表：每操作追加执行数量与截止 T 的完成状态；展示个体点，不只给均值。

### B3：范围与完成代价（必需 CPU；GPU 验证可选）

- 三策略×同 run/新 run×三个调度顺序=18 个操作，仅在接受后回执丢失条件下。
- 新 run 的 seed/语义输入保持相同，用 operation_id 表示相同意图；仍不宣称产品可跨 run 去重。
- CPU 两阶段已知-ID 恢复另加三策略×三个调度=9 个操作，明确这是已有恢复功能。
- 成功标准：范围外重试如实暴露、完成代价可测、已知-ID 恢复不归功于 unknown 守卫。
- 负结果：若用户仅需换 run 即可绕过，主张必须保持 run 局部；不泛化为端到端 exactly-once。
- 图表：作用域图，以及完成/阻塞/追加执行联合表。

### B4：证据的实际判读增量（必需，复用记录，不新增 GPU）

- 冻结从 B1/B2 获取的完整记录，再生成三种视图：客户端状态、传统原始日志、契约化证据。
- 预先定义问题：接受是否已证实、执行数是否可确定、原 run 是否完成、是否有足够证据自动恢复。
- 以独立保存的完整受控记录为答案依据；缺证据允许 unknown；不能用待测 exporter 的答案当真值。
- 指标：错误肯定数、正确肯定数、unknown 数及每题覆盖率。若原始日志也能答对，贡献只能是结构化/机器可检验，不宣称信息更多。
- 不做未批准的人类参与者研究，不把脚本判读速度称为开发者效率。
- 可增加删除字段的诊断图，但不通过只删竞争方关键字段来制造优势。

## 指标与分析规则

基本单位是逻辑操作，分母按故障条件、策略、作用域分别列出。
- 额外执行：同一逻辑操作经后端证据区分出的 max(0,E−1)。事件累计值不等于 E；无法判定时为 unknown，不填零。
- 提交数：代理可证实的 POST 数；接受、执行与产物各自分开。
- 完成：截止 T 原 run 的持久状态和约定产物证据满足成功条件；新 run 成功另列，不能覆盖原 run unresolved。
- 误拦方向：在可证明未接受且恢复请求被守卫拒绝的操作中报告拒绝数/该条件操作数。另报已接受场景的安全阻塞。
- 时延：完成者的完成时间和未完成者在 T 的删失状态共同报告，不只统计成功者。
- 证据覆盖：可判定操作/所有计划操作；基础设施失效、注入失败、超时均保留并说明。

所有实验均为受控故障条件，比例不能称为自然部署失败率或自然重复执行率。
小规模先报告原始配对结果、范围与差异，不承诺显著性；确定性重复不是独立样本。
不按是否产生有利结果追加 seed。扩大样本必须另写固定预算及分析修订。

## 创新性与转向条件

- 若 P-guard 与 P-stop 在行为和完成代价上完全等价，且证据契约没有可展示的判读增量：停止 Regular 升级，保留诚实的 Tool/工程报告。
- 若唯一差异是 UI 文案或 JSON 格式，不声称新恢复算法。
- 如需增加真正的自动 reconciliation、幂等 token 或持久去重，这是新的方法设计与评估，不在本提案顺手加入。
- 若效果依赖一个故障调度或单一后端，报告局部边界；第二后端/多模型/吞吐压测均为可选，当前不排期。
